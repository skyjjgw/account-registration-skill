# 邮箱、页面会话与进度

## 两个网页往返

注册页 A 和邮箱页 B 是两个真实标签页，各自保留状态；流程模块的执行顺序可为 A → B → A，第二次 A 指向同一页句柄。回到 A 时只激活并填入内容，不重新导航。若必须刷新或重建页面，先确认验证事务仍有效。

同一账号的标签页可共享允许的浏览器上下文；不同账号使用分离会话以免把上一账号的登录状态当成新账号成功。不要复制 Cookie 来规避登录或验证。新建独立上下文后，邮箱也可能需要重新登录，原内置浏览器中的邮箱会话不会自然继承。

## 邮件选择

对本次发码记录 `requested_at`，接受邮件至少满足：
1. 收件人匹配本次邮箱；汇总邮箱尤其要检查 To 字段。
2. 来自预期网站的正常验证邮件，并且内容与本次动作一致。
3. 时间晚于本次请求（考虑邮件服务器显示时区），验证码未超过邮件注明的有效期。
4. 提取位置是这一封邮件的验证码区域，而非整个收件箱或含日期、其他订单号的正文。

六位数字正则只解决文本提取，不解决邮件身份、时效或请求关联。重发后清除旧候选，只等待最新请求对应的邮件；不要连续重复点击发码。轮询到站点实际有效期或合理等待上限就暂停检查，不无限刷新。

历史邮箱站点为 `https://mail.zshgdemoni.me/inbox`。曾观察到登录邮箱名与打开邮件的收件人不同，因此不能依靠右上角账号名确认邮件归属。邀请码、账号名、密码不能写成跨批次永久默认值；实际出现邀请要求时使用当前用户提供的信息。

## 账号编号与中断记录

如用户已授权顺序编号，记录前缀、起始编号、步长和最小补零位数。`user09` 后是 `user10`；编号超过补零位数不截断、不回卷。先检查已有结果和已预留编号，避免撞号。只生成账号字符串不等于邮箱或平台账号已创建。

每个账号保存最少必要的本地进度，例如：

```json
{
  "account_id": "test020",
  "site": "https://example.test",
  "number": 20,
  "stage": "verification_requested",
  "status": "needs_review",
  "requested_at": "2026-09-27T10:00:00Z",
  "last_observation": "发码已确认；尚未读取新邮件"
}
```

建议阶段：mailbox_ready、verification_requested、code_received、verification_submitted、onboarding、completed。状态使用 in_progress、needs_review、success、failed、skipped，注明实际证据。

开始外部提交前写入 in_progress；结果明确后再记 success。异常退出留下的 in_progress 需要核对网站，不能自动归入失败后重试。程序只返回 0 时仍需核对成功断言是否覆盖真正完成状态。多个进程不能同时消费同一批次进度。

批次遇到状态不明的提交、连续失败或人机验证时停止新增账号，按当前工具能力处理；有明确数量就完成该数量，不自动扩大。用户要求停止后保留断点，恢复时从已核对的进度继续。
